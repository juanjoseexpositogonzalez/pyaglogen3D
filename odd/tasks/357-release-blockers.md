- **T18** — S2-S4, S7, S9 — **in progress** — Replace the two-store admission decision for asynchronous box-counting with a single authority: the durable `ParametricStudy` row decides whether a run is in flight, and the Celery result backend keeps only progress and status ownership. Contract:
  1. **Authority.** Admission reads only the row-locked study. `box_counting_task_state` in `pending`, `dispatched` or `running` with an unexpired lease means in flight and answers 409; `finished`, `cancelled` and empty never block. No result-backend read participates in admission.
  2. **Lease by phase.** `box_counting_task_reserved_at` records when the current phase began: the publisher sets it at reservation, stamps it again when the dispatch is marked published, and the worker refreshes it when it claims the task. Each of the three phases has its own bound. A `pending` row means a publisher is reserving and enqueueing right now, which lasts seconds, so it keeps the existing 30-second publisher lease. A `dispatched` row means the broker accepted the message, which may wait the whole queue, so it expires after the 60-minute queue expiry plus a 5-minute grace, because Celery itself discards an older message. A `running` row expires after the 60-minute hard runtime plus the same grace. This replaces the composite 7,500-second lease, which existed only because the marker could not tell the phases apart. Collapsing `pending` into the queued bound is explicitly wrong: it would keep a study blocked for 65 minutes after a publisher crash that the 30-second lease resolves in seconds.
  3. **Recovery.** An expired `pending` or `dispatched` claim whose stored payload does not conflict with explicitly supplied parameters is republished with its original task id and payload, and the 202 discloses `recovered` plus every effective parameter, `force` included.
  4. **Supersede.** An expired claim that conflicts with explicitly supplied parameters — `points_per_sphere`, `precision`, `windowed` or `force` — is retired with a transactional `cancelled` tombstone and the caller's own parameters are dispatched under a fresh task id, or run synchronously below the threshold. A concurrent worker claim wins and answers 409.
  5. **No cross-store cleanup inside a transaction.** Result-backend records are never written while a database transaction is open. Any best-effort release of a superseded task's records happens after commit and may fail harmlessly, because no admission decision depends on it.
  6. **Deploy window.** A run dispatched before this change has no durable row. While that window lasts, and only when the durable state is empty, admission consults the legacy `bc-inflight-<study_id>` marker and fails closed on an unreadable backend. This is the sole remaining marker read and is removed once no legacy run can survive, which is bounded by queue expiry plus runtime plus grace.
  7. **Preserved.** Worker row-locked claiming and `Ignore()` for duplicate, stale, terminal or unowned deliveries; ownership-gated status reads with a generic 404; request precedence and persisted-shape validation; the 60-minute queue expiry; synchronous runs below the threshold that need no result backend.
  8. **Removed.** `bc-inflight-<study_id>` as an admission authority, the `recovering` cleanup flag, and the composite in-flight lease.
